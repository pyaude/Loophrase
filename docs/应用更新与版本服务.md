## 1. 背景

Loophrase 当前通过 GitHub Actions 构建 APK 并以 Artifact 形式分发，用户需要手动访问 GitHub Actions 页面下载安装。存在以下问题：

1. **用户无法感知新版本** — 没有任何应用内提示机制。
2. **分发链路断裂** — 构建成功后仅有钉钉通知（含 GitHub 链接），用户需理解 GitHub 操作才能获取 APK。
3. **版本号硬编码** — 设置页版本号为写死字符串，与实际构建版本脱节。

### 1.1 目标

| 编号 | 目标 | 验收标准 |
| --- | --- | --- |
| U-01 | 应用启动时自动检测新版本 | 有新版本时弹出更新提示 |
| U-02 | 用户可在应用内手动触发更新检查 | 设置页有「检查更新」入口 |
| U-03 | 用户确认后下载 APK 并安装 | 下载进度可见，下载完成自动唤起安装器 |
| U-04 | 支持强制更新 | 低于最低版本时不可跳过 |
| U-05 | 后端版本服务可管理多版本发布 | 管理员可上传 APK、填写 changelog |
| U-06 | CI 构建完成后自动发布到版本服务 | 构建成功后 APK 自动上传到后端 |

### 1.2 非目标

- 不使用 OTA（expo-updates）热更新 — 原生模块变更无法通过 OTA 推送。
- 不上架 Google Play — 当前阶段保持自分发模式。
- 不实现 iOS 更新 — iOS 无法通过下载 IPA 自安装，暂不处理。
- 不实现静默安装 — Android 安全策略不允许，必须用户确认。

## 2. 方案选型

### 2.1 方案对比

| 方案 | 适用场景 | 局限 | 结论 |
| --- | --- | --- | ✗ |
| A. expo-updates (OTA) | JS-only 变更 | 无法更新原生代码 | 单独不够用 |
| B. 自建 FastAPI + APK 下载 | 完整版本更新 | 用户需手动安装 | **采用** |
| C. 混合 (A+B) | 覆盖所有场景 | 复杂度高，MVP 不需要 | 未来考虑 |

**最终选择：方案 B — 自建 FastAPI 版本服务 + APK 下载安装。**

理由：
- 项目依赖 expo-video / expo-audio / expo-sqlite 等原生模块，版本迭代常涉及原生变更。
- OTA 在原生版本不匹配时会导致崩溃，风险高于收益。
- FastAPI 后端可作为未来转写服务、通知服务等的基础设施。

### 2.2 Android 安装限制说明

Android 安全策略禁止应用静默安装 APK，完整流程必须为：

```
检测新版本 → 提示用户 → 用户确认 → 下载 APK → 调用系统安装器 → 用户再次确认安装
```

需要处理：
- Android 8+ 需引导用户开启「安装未知来源应用」权限（针对本 App）。
- 下载需考虑网络中断、存储空间不足等异常。
- APK 需存放在 App 可访问的目录（`cacheDirectory`）。

## 4. API 规范

### 4.1 检查更新

```
GET /api/v1/check-update?platform=android&version=0.1.0
```

**响应 — 有更新：**

```json
{
  "has_update": true,
  "latest_version": "0.2.0",
  "min_required_version": "0.1.0",
  "is_force_update": false,
  "changelog": "1. 新增横屏全屏播放\n2. 修复字幕导入问题\n3. 优化复读间隔控制",
  "download_url": "https://server.example.com/api/v1/download/Loophrase-0.2.0.apk",
  "file_size": 45678901,
  "published_at": "2026-08-07T10:00:00Z"
}
```

**响应 — 无更新：**

```json
{
  "has_update": false,
  "latest_version": "0.1.0"
}
```

**字段说明：**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `has_update` | boolean | 是否有新版本 |
| `latest_version` | string | 服务端最新版本号（semver） |
| `min_required_version` | string | 最低兼容版本，低于此版本强制更新 |
| `is_force_update` | boolean | 当前请求版本是否需要强制更新 |
| `changelog` | string | 更新日志（纯文本，`\n` 分行） |
| `download_url` | string | APK 下载地址 |
| `file_size` | number | APK 文件大小（字节），用于预估下载时间 |
| `published_at` | string | 发布时间（ISO 8601） |

### 4.2 下载 APK

```
GET /api/v1/download/{filename}
```

- 支持 `Range` 请求头（断点续传）。
- 响应头包含 `Content-Length`、`Content-Type: application/vnd.android.package-archive`。
- 流式传输，避免大文件全量加载到内存。

### 4.3 版本列表

```
GET /api/v1/versions?platform=android
```

```json
{
  "versions": [
    {
      "version": "0.2.0",
      "changelog": "...",
      "file_size": 45678901,
      "published_at": "2026-08-07T10:00:00Z"
    },
    {
      "version": "0.1.0",
      "changelog": "首个 MVP 版本",
      "file_size": 42000000,
      "published_at": "2026-07-15T10:00:00Z"
    }
  ]
}
```

### 4.4 发布新版本（管理接口）

```
POST /api/v1/admin/publish
Authorization: Bearer <ADMIN_TOKEN>
Content-Type: multipart/form-data
```

**表单字段：**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version` | string | 版本号（semver，如 `0.2.0`） |
| `platform` | string | 平台（目前固定 `android`） |
| `changelog` | string | 更新日志 |
| `min_required_version` | string | 最低兼容版本（默认 `0.0.0` = 不强制） |
| `apk` | file | APK 文件 |

### 4.5 删除版本（管理接口）

```
DELETE /api/v1/admin/versions/{version}
Authorization: Bearer <ADMIN_TOKEN>
```

## 5. 数据模型

后端使用 SQLite 存储版本元数据：

```sql
CREATE TABLE app_version (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  version             TEXT NOT NULL UNIQUE,        -- 语义化版本号，如 0.2.0
  platform            TEXT NOT NULL DEFAULT 'android',
  changelog           TEXT,
  min_required_version TEXT NOT NULL DEFAULT '0.0.0',
  file_path           TEXT NOT NULL,               -- APK 文件在服务器上的路径
  file_size           INTEGER NOT NULL,
  is_active           INTEGER NOT NULL DEFAULT 1,  -- 0=已下架，1=正常
  published_at        TEXT NOT NULL,               -- ISO 8601
  created_at          TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_version_platform ON app_version(platform, is_active);
```

## 6. 版本比较规则

采用语义化版本（Semantic Versioning）比较：

```
格式: MAJOR.MINOR.PATCH (如 0.2.1)

比较规则:
  0.1.0 < 0.1.1 < 0.2.0 < 1.0.0 < 1.1.0

强制更新判定:
  is_force_update = (current_version < min_required_version)
```

后端使用 Python `packaging.version` 或自实现 semver 解析。

## 7. App 端交互设计

### 7.1 自动检查（启动时）

```
App 启动
  │
  ▼
后台静默调用 checkForUpdate()
  │
  ├─ 无更新 / 请求失败 → 静默跳过
  │
  ├─ 有更新 + 非强制 → 底部弹窗
  │     ┌─────────────────────────┐
  │     │  📦 发现新版本 v0.2.0    │
  │     │                         │
  │     │  1. 新增横屏全屏播放      │
  │     │  2. 修复字幕导入问题      │
  │     │  3. 优化复读间隔控制      │
  │     │                         │
  │     │  [稍后]      [立即更新]  │
  │     └─────────────────────────┘
  │
  └─ 有更新 + 强制更新 → 全屏遮罩弹窗（不可关闭）
        ┌─────────────────────────┐
        │  ⚠️ 需要更新到 v0.2.0    │
        │                         │
        │  当前版本过低，需要更新    │
        │  才能继续使用             │
        │                         │
        │      [立即更新]          │
        └─────────────────────────┘
```

### 7.2 下载与安装流程

```
用户点击「立即更新」
  │
  ▼
检查存储空间 (file_size)
  │
  ├─ 空间不足 → 提示用户清理
  │
  └─ 空间充足
      │
      ▼
    下载 APK（显示进度条）
      ┌─────────────────────────┐
      │  ⬇️ 下载中 67%           │
      │  ████████████░░░░░░     │
      │  预计剩余 12 秒           │
      └─────────────────────────┘
      │
      ├─ 下载失败 → [重试] 按钮
      │
      └─ 下载完成
          │
          ▼
        调用 expo-intent-launcher 唤起系统安装器
          │
          ├─ 未授权安装 → 引导用户开启权限
          │
          └─ 已授权 → 系统安装界面 → 安装完成
```

## 11. 安全考虑

| 风险 | 措施 |
| --- | --- |
| APK 被篡改 | 后端可计算 SHA256 并随版本信息下发，App 端可选校验 |
| 管理接口被滥用 | Token 鉴权；可选 IP 白名单 |
| 下载流量耗尽 | 可选限流（每 IP/天）；未来接 CDN 分发 |
| 版本号伪造 | 版本比较在后端完成，客户端只传当前版本号 |
